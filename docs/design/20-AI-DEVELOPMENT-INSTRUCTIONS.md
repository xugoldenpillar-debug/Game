# 20 — AI 总开发执行指令

> 本文件用于 Codex/Claude/其他代码代理接手仓库时作为最高层开发约束之一。实现前必须同时阅读 `docs/design/` 全部文档。

## 1. 项目目标

实现一款原创的 2D 火柴人横版动作网页游戏。参考经典火柴人清版动作游戏的爽快节奏，但不得直接复制他人受版权保护的角色、美术、关卡、名称、音频、剧情或具体资产。所有最终内容必须原创。

目标特征：丰富火柴人动作、徒手格斗、冷兵器、大量枪械、投掷物、环境互动、可破坏场景、长剧情战役、敌人AI、Boss、成长、伙伴、支线和挑战模式。

## 2. 开发优先级

永远按以下顺序做判断：
1. 游戏能运行且不破坏现有功能。
2. 战斗手感和输入响应。
3. 正确的系统架构和数据驱动。
4. AI与关卡可玩性。
5. 内容数量。
6. 视觉润色。

禁止为了快速展示大量内容而绕过核心架构。

## 3. 强制工程原则

- TypeScript strict。
- 不允许在单个 Scene 文件中堆积整个游戏逻辑。
- 武器、敌人、技能、任务、掉落数据化。
- 使用稳定ID。
- 状态机有明确进入/退出条件。
- 战斗时间逻辑与帧率解耦。
- 高频对象使用对象池。
- 所有外部数据在读取时校验。
- 存档带版本和迁移。
- `main` 任何提交都必须可启动。

## 4. 修改流程

每次任务：
1. 阅读相关设计文档和现有代码。
2. 找到最小正确实现边界。
3. 优先复用现有系统，不重复造相同模块。
4. 实现。
5. 添加/更新测试。
6. 运行 typecheck、test、build。
7. 手工检查关键游戏流程（若具备运行环境）。
8. 更新相关设计/开发说明。
9. 总结改动、风险、未完成项。

禁止在测试失败情况下假装完成。

## 5. 禁止事项

- 不要用 `any` 大面积绕过类型。
- 不要通过 `setTimeout` 堆叠临时战斗逻辑。
- 不要在多个系统复制伤害计算。
- 不要把武器数值散落在代码常量。
- 不要让AI直接读取玩家按键做“预知”。
- 不要使用无法追踪来源的版权素材。
- 不要通过增加敌人血量解决所有难度问题。
- 不要为了动画完整播放而吞掉玩家输入。
- 不要删除现有功能来让新功能测试通过，除非设计明确要求。

## 6. Combat Definition of Done

新增攻击必须包含：动作状态、输入规则、前摇/生效/后摇、hitbox、伤害、poise、击退、动画key、VFX/SFX hook、取消窗口、受击交互、测试。

新增枪械必须包含：definition、runtime state、射击模式、弹药、装填、后坐、散布、距离衰减、命中特效、音效hook、拾取/装备、UI、测试。

## 7. Enemy Definition of Done

新增敌人必须包含：definition、AI profile、至少一项独特行为、距离偏好、武器/能力、动画映射、受击/死亡、掉落、Encounter成本、调试可视化信息和测试场景。

## 8. Mission Definition of Done

新增任务必须包含：地图引用、目标、失败条件、检查点、遭遇、事件、奖励、任务开始/完成流程；死亡和重载后状态可恢复；不能因随机掉落阻断。

## 9. 性能规则

任何新增粒子、子弹、敌人或Ragdoll系统都必须考虑批量/池化。禁止每帧全地图查找实体。需要邻近查询时使用空间分区或局部集合。

## 10. Debug First

复杂系统必须带调试显示。尤其：hitbox、AI状态、导航、Encounter预算、任务状态、伤害管线。开发代理不应只靠猜测游戏内部状态。

## 11. 提交粒度

一个提交尽量解决一个明确问题。提交信息格式推荐：
`feat(combat): add melee hitbox pipeline`
`feat(ai): add cover selection`
`fix(save): restore mission checkpoint state`
`data(weapons): add shotgun definitions`

## 12. 代码审查自检

提交前回答：
- 是否引入重复系统？
- 是否存在隐藏硬编码？
- 是否破坏存档？
- 是否在低帧率下行为变化？
- 是否有状态无法退出？
- 新内容能否仅通过数据继续扩展？
- 是否测试了死亡/暂停/切关/重载？

## 13. 当前实施顺序

若仓库仍只有设计文档，则第一目标不是一次完成正式版，而是严格按 `19-DEVELOPMENT-ROADMAP.md`：工程基础 → Combat Sandbox → Vertical Slice。只有 Vertical Slice Gate 通过后才批量生产48关与100武器。

## 14. 完成口径

“已实现”只能用于代码确实存在、可构建、测试通过的内容；仅写文档、TODO、接口或假数据必须明确标记为“规划/骨架/未完成”。

最终目标是交付一款玩家打开网页即可从头到尾游玩的完整游戏，而不是一个看似文件很多但核心流程无法通关的原型。
